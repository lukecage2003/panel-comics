# Phase 3 · 07 — Cahier des charges du lot 3.1 : fondations backend et préparation du client

Statut : **à valider avant exécution**. Le prompt d'exécution est dans [`08-lot-3.1-prompt.md`](08-lot-3.1-prompt.md).

## 1. Objectif
Poser un backend **reproductible, versionné, testé et sûr**, sans créer de compte cloud, sans dépense et sans changer le comportement de l'application. À la fin du lot :
- on peut recréer la base à l'identique depuis le dépôt ;
- l'isolation entre utilisateurs (RLS) est prouvée par des tests ;
- le client sait dire ce qui serait synchronisé.

## 2. Hors périmètre (explicitement)
- Aucun projet Supabase créé, aucune inscription à un service, aucune clé réelle.
- Aucune authentification dans l'interface, aucun envoi réseau vers un backend.
- Aucune fonction `sync_push`/`sync_pull` opérationnelle (prévues au lot 3.4). Le lot 3.1 crée seulement les tables qu'elles utiliseront.
- Aucun nouveau store IndexedDB, aucune hausse de version de `panel-library` (v3) ou de `panel-catalog` (v4).
- Aucune modification des données locales existantes.

### 4.2 Tables initiales (schéma `app`), et seulement celles-ci
| Table | Clé | Colonnes principales | Relations |
|---|---|---|---|
| `profiles` | `user_id` | `handle citext unique`, `display_name`, `avatar_path`, `bio`, `locale`, `preferred_market`, `created_at`, `updated_at` | → `auth.users` cascade |
| `user_settings` | `user_id` | `prefs`, `notifications`, `privacy` (jsonb, privé par défaut), `rev`, `updated_at` | → `auth.users` cascade |
| `devices` | `id uuid` | `user_id`, `label`, `platform` (check `web`/`android`), `app_version`, `created_at`, `last_seen_at`, `last_sync_rev`, `revoked_at` | → `auth.users` cascade ; index `(user_id)` |
| `copies` | `(user_id, id)` | colonnes de synchronisation communes (`04` § 2), colonnes extraites `series_key`, `issue_number`, `is_wishlist` | → `auth.users` cascade ; index `(user_id, rev)` |
| `locations` | `(user_id, id)` | communes + `parent_id`, `kind` | idem |
| `pulls` | `(user_id, id)` | communes + `series_key`, `release_date` | idem |
| `series_follows` | `(user_id, id)` | communes | idem |
| `reading_progress` | `(user_id, id)` | communes + `guide_id`, `entry_id` | idem |
| `user_sync_state` | `user_id` | `last_rev bigint` | → `auth.users` cascade |
| `sync_ops` | `(user_id, op_id)` | `applied_rev`, `result jsonb`, `created_at` | index `(created_at)` pour la purge |
| `sync_conflicts` | `id uuid` | `user_id`, `entity`, `entity_id`, `field`, `local_value`, `server_value`, `base_rev`, `server_rev`, `device_id`, `created_at`, `resolved_at`, `resolution` | index `(user_id, resolved_at)` |

Schémas : `app` contient **uniquement** les données personnelles. Les schémas `catalog`, `editorial`, `media` et `signals` sont **réservés** à Explorer 2.0 et aux services communs (Phase 4), `community` au futur domaine Community ; ils et ne sont pas créés ; le banc de tests doit néanmoins accepter des migrations multi-schémas.

`user_guides` est **reporté au lot 3.4** (synchronisation facultative). Aucune table communautaire, premium ou de catalogue.

Contraintes :
- `data` ≤ 64 Ko (`octet_length(data::text)`) ;
- `id` non vide, ≤ 100 caractères ;
- `schema_version` ≥ 1 ;
- `deleted_at` nullable.

### 4.3 Sécurité initiale
- `alter table … enable row level security` sur **toutes** les tables du schéma `app`.
- Politiques `to authenticated` avec `(select auth.uid()) = user_id`, distinctes pour `select`, `insert`, `update` et `delete`.
- `sync_ops`, `sync_conflicts` et `user_sync_state` : lecture seule pour l'utilisateur ; l'écriture passera par les fonctions du lot 3.4.
- `revoke all` pour `anon` sur le schéma `app`.
- Déclencheur `rev` (`security definer`, `set search_path = ''`) : incrémente `user_sync_state.last_rev` et l'affecte à la ligne.
- Index sur toutes les colonnes utilisées par les politiques.
- **Aucun secret** dans le dépôt : `config.toml` sans valeur sensible, `.env.example` vide, `seed.sql` fictif.

## 5. Client : préparation sans changement de comportement
- `SYNC_DOMAINS` : liste déclarative (nom, source locale, table serveur, synchronisé oui ou non, raison), reprenant `04` § 1.
- `Panel.sync.readiness()` (lecture seule) renvoie :
  - le nombre de fiches par domaine ;
  - les fiches sans identifiant ou en double (réutilise `Panel.catalog.idReport()`) ;
  - les couvertures `data:` de plus de 256 Ko ;
  - les clés exclues (secrets) ;
  - l'estimation du volume (Ko).
- `PANEL_SYNC_ENABLED = false` : aucune branche de code active.
- Aucune écriture, aucune requête réseau, aucune interface visible.

## 7. Critères d'acceptation mesurables
| # | Critère | Mesure |
|---|---|---|
| 1 | Reproductibilité | `npm ci && npm run test:db` depuis un clone propre : 0 échec, en moins de 60 s |
| 2 | Migrations | Les 6 migrations s'appliquent dans l'ordre sur une base vide ; le schéma obtenu correspond à `schema.test.js` (tables, colonnes, types, contraintes, index) |
| 3 | Intégrité | Clés primaires, clés étrangères `on delete cascade`, contraintes de taille testées (insertion invalide refusée) ; suppression d'un utilisateur ⇒ 0 ligne restante dans les 11 tables |
| 4 | RLS | Pour chaque table : l'utilisateur A ne lit, ne modifie ni ne supprime aucune ligne de B (0 ligne visible) ; `anon` : 0 ligne et écriture refusée ; RLS activée sur 100 % des tables `app` (requête sur `pg_class.relrowsecurity`) |
| 5 | `rev` | Strictement croissant par utilisateur sur 1 000 écritures ; indépendant entre deux utilisateurs |
| 6 | Secrets | `npm run check:secrets` : 0 correspondance (motifs de clés JWT, `service_role`, `sk_`, clés Comic Vine ou Metron, mots de passe) dans les fichiers suivis ; `.secrets/` et `.env` jamais suivis (`git ls-files`) |
| 7 | Sauvegarde | Avant toute modification : copie de `index.html`, `run-all-tests.js`, `sw.js` et `.gitignore` (`*.backup.<date>-lot31`) ; aucune sauvegarde existante supprimée (inventaire avant et après identique, ajouts exceptés) |
| 8 | Restauration | Runbook de restauration rédigé ; test de bout en bout seulement en local (dump puis restauration PGlite ou Docker si disponible), résultat consigné |
| 9 | Compatibilité front | `node run-all-tests.js` : 28 tests existants + 1 nouveau, tous au vert ; `Panel.sync.readiness()` ne modifie ni localStorage ni IndexedDB (empreinte avant et après identique) |
| 10 | Aucune régression locale | Application ouverte hors ligne : collection, Explorer, calendrier, sauvegarde et restauration JSON fonctionnent comme avant |
| 11 | Qualité des tests | Chaque politique RLS a au moins un test positif et un test négatif ; les tests échouent si la RLS est désactivée (vérification par mutation, documentée) |
| 12 | Documentation | README backend et 4 runbooks présents ; aucun lien mort (vérification par script) |

## 9. Risques du lot
| Risque | Parade |
|---|---|
| PGlite différent de Supabase | Tests rejoués sous Docker dès que possible ; écarts documentés |
| Superutilisateur qui contourne la RLS dans les tests | Rôles non privilégiés, test de mutation (§ 7 n° 11) |
| Dépendance npm compromise | Version figée, `package-lock.json` versionné, revue de la liste des dépendances (PGlite seulement, si possible) |
| Ajout d'un `package.json` à la racine qui gêne Android ou `serve.js` | Vérifier que `android-app/` garde son propre `package.json` et que `serve.js` n'en dépend pas |
